# MCP spec ล็อกเที่ยงคืนนี้ — protocol กลายเป็น stateless, OAuth 2.1 คลุมทั้ง ecosystem แล้ว

## TL;DR
- **28 ก.ค. 2026 = D-Day ของ MCP** — spec revision ที่ใหญ่ที่สุดตั้งแต่ launch (พ.ย. 2024) จบ 10-week validation window เที่ยงคืนนี้ (Bangkok TZ)
- **Protocol กลายเป็น stateless** — เอา session handshake ทิ้ง, เปิดทางให้ MCP server อยู่หลัง round-robin load balancer ธรรมดา แทน pinned connection แบบ HTTP/1.1
- **Authorization = OAuth 2.1 + OpenID Connect** — MCP server เป็น "OAuth 2.1 resource server" อย่างเป็นทางการ, เข้ากับ enterprise SSO/gateway ที่มีอยู่แล้วโดยไม่ต้อง custom broker
- **Extension framework ใหม่** — MCP Apps (server-rendered UI) + Tasks (long-running work) เปิดทาง surface พ้น "tool call = 1 request-response" ที่ผูก MCP ไว้ตั้งแต่ launch

## เกิดอะไรขึ้น

10 สัปดาห์ที่แล้ว (21 พ.ค.) ทีม maintainer ของ Model Context Protocol เผยแพร่ release candidate ของ spec ตัวใหม่ที่ตั้งชื่อตามวันที่ freeze — **MCP 2026-07-28** — พร้อมประกาศชัดว่าเป็น "largest revision since launch" ที่มาพร้อม breaking change ระดับ architectural. Validation window ปิดวันนี้ และ SDK ทุกภาษา (Python, TypeScript, Java, Rust) พร้อมออก version bump ตามภายใน 72 ชั่วโมง

หัวใจของ revision นี้คือคำเดียว: **stateless**. ตั้งแต่ launch ปี 2024, MCP มี session handshake ที่ pin client-server ไว้กับ single instance — pattern ที่ทำงานดีตอน MCP รันบน laptop developer แต่พังทันทีเมื่อ enterprise พยายาม deploy หลัง edge load balancer หรือ Kubernetes service mesh. Spec ใหม่ทำให้ทุก request routable แยกกัน, headers ระบุ context เอง, session state (ถ้าจำเป็น) push ไปที่ application layer

Layer authorization ก็ถูก rewrite ทั้งชั้น. เดิม MCP ให้ implementer เลือก auth scheme เอง — ส่วนใหญ่ลงเอยด้วย bearer token custom หรือ shared secret ใน env — spec 2026-07-28 บังคับให้ MCP server เป็น **OAuth 2.1 resource server อย่างเป็นทางการ**, รับ token ที่ issued จาก standard OAuth authorization server, และ integrate กับ OpenID Connect ได้ทันที. แปลว่า enterprise ที่ deploy MCP หลัง Okta/Azure AD/Google Workspace ไม่ต้องเขียน integration ใหม่ — reuse SSO stack เดิม

ที่ under-reported กว่าคือ **extension framework**. MCP Apps เปิดให้ server render UI element กลับไปหา client (คล้ายกับที่ Slack Blocks ทำใน chat), และ Tasks ทำให้ server รับ long-running work ได้โดยไม่ต้อง block connection. สองอย่างนี้ break assumption ว่า MCP = tool call = 1 request-response ที่ผูก ecosystem ไว้ตั้งแต่แรก

Timeline ตอนนี้ชัด: 28 ก.ค. spec ล็อก → 30 ก.ค. SDK release → Anthropic, OpenAI, Google, Microsoft ต้อง align client ภายใน 30 วัน (ถ้าไม่อยาก fragment ecosystem). Cloudflare AI Gateway, WorkOS AuthKit for MCP, และ Alterion Draco (runtime governance — ดู brief #04) เตรียม compatibility layer เพื่อรับ enterprise migration

## ทำไมสำคัญ

นี่คือ **coming-of-age moment** ของ MCP. Spec เดิมออกแบบสำหรับ developer ที่รัน single laptop, single server — pattern ที่ scale ไม่ได้พ้น 10K MCP server ที่มีตอนนี้. Spec ใหม่ออกแบบสำหรับ **10 ล้าน MCP server ในปี 2028** — protocol ที่พร้อม run เหมือน HTTP: ทุก server behind CDN, ทุก request auth ผ่าน OAuth, load balancer เห็นทุกอย่าง

Pattern นี้เคยเกิดกับ **gRPC ปี 2016** (จาก experimental Google → CNCF graduated) และ **GraphQL ปี 2018** (จาก Facebook internal → Apollo, Hasura, enterprise adoption). ทุก protocol ที่จะกลายเป็น infrastructure ต้องผ่าน revision ที่ trade elegance ของ v1 กับ realities ของ enterprise deployment — และ MCP กำลังผ่านช่วงนั้นตรงหน้าเรา

จุดที่น่าจับตาคือ **timing กับ MCP vulnerability disclosure**. ต้นเมษายน OX Security เผยแพร่ report ว่า official SDK มี design flaw ระดับ RCE — Anthropic ตอนนั้นปฏิเสธว่าเป็น bug. Spec 2026-07-28 ไม่ mention vulnerability ตรง ๆ แต่การย้ายไป OAuth resource server + stateless (ไม่มี STDIO pinning) = โครงสร้างที่ทำให้ attack surface ของ vulnerability เดิมแคบลงมาก. Anthropic ไม่พูดคำว่า "แก้" แต่ architecture ใหม่คือคำตอบทางเทคนิคของคำถามที่ industry ถามมา 3 เดือน

Signal ต่อจากนี้: **client fragmentation**. Cursor, Windsurf, Zed, Claude Desktop, ChatGPT — ทุกเจ้าต้องเลือก migrate ทันทีหรือ hold at old spec. คนแรกที่ launch "MCP 2026-07-28 native" client จะได้ enterprise deal ก่อน; คนที่ hold จะเจอ shadow spec ที่ diverge (คล้าย IE6 อยู่นานเกินไปในยุค web standard)

## มุม AI Agent Platform

**Builders:** ทุก MCP server ที่ build ใน 12 เดือนที่ผ่านมาต้อง audit spec compatibility ภายในสิ้นสัปดาห์. ถ้ายังพึ่ง session state ใน memory → migrate ไป external store (Redis/DynamoDB) ทันที; ถ้ายัง auth ผ่าน bearer token custom → wrap ด้วย OAuth 2.1 resource server library (WorkOS, Auth0, Okta ทุกเจ้ามี MCP-flavored SDK ออกภายในสัปดาห์). ทีมที่ hold at old spec = pay technical debt ใน Q4 พร้อมกับพลาด enterprise pipeline

**Users / business:** ถ้า enterprise ยังไม่มี MCP gateway strategy — 28 ก.ค. คือ deadline ที่ CISO จะเริ่มถาม. Cloudflare, WorkOS, Kong, Alterion ทุกเจ้ามี compatible offering; แต่ที่สำคัญกว่าคือ **catalog + policy**: MCP server ไหน sanctioned, endpoint ไหน block, per-tool rate limit. Enterprise ที่ deploy stateless spec ใหม่ + OAuth = unlock horizontal scale ที่รอมาทั้งปี (session pinning เคยจำกัดที่ single-region deployment)

**Ecosystem:** สำหรับ Enabridge — window ที่ **"MCP-native for regulated SMB Thai"** ยังเปิด. Thai bank / hospital / gov ต้องการ MCP ที่มี OAuth + audit + Thai-hosted; spec ใหม่ทำให้ปัญหา infra ง่ายลง แต่ปัญหา trust + compliance ยัง open. ใครที่เขียน "MCP 2026-07-28 compliant + audit-ready + Thai PDPA" ใน positioning ภายใน 30 วัน = ยึด SME/SET100 tier ก่อน hyperscaler ตามมา
